2026-10-03 実機確認: CAN2の20MHz発振子に合わせたビットタイミング、SDの書込み待ち中のSPI解放、停止中のSD読出し競合を修正。125/250/500/1000kbpsの外部折返しと約100フレーム/秒の継続試験で計14,400フレームが一致。SDファイル切替を含む同時取得でも欠落0。試験送信は一時ファームのみ。通常ファームはCAN1がリッスンオンリー、CAN2がセンサーハブ受信とACKのための通常モードで、アプリケーション用CANフレームは送信しない（CAN2の通常モードを実機へ書き込んだのは2026-10-09。それまでの稼働版はCAN2も受信専用だった）。詳細は `outputs/hardware_check_20261003/RESULT.txt`。

`ecologger_v2.ino` → `logger_impl.h` と `sd_logger.h`。UNO Q STM32U585 / Arduino Zephyr core 0.52.0。

- BNO055: I2C2 0x28/29、400kHz、NDOF 100Hz、A5の高加速度割り込み。
- MAX-M10M: I2C 0x42、4衛星系統/10HzのRAM設定。OTPの再書き込みなし。NAV-PVTは10Hz、NAV-SAT・NAV-SLASは1秒に1回（SP-7-8、下）。

  - 動き：起動したCAN1はリッスンオンリー。1秒に50フレーム以上受けて車が動いていると分かってから、自動再送なし（DAR）の通常モードに切り替える（`obd`の状態1）。送信エラー（TEC 16以上、エラーパッシブ、バスオフ）が出たらリッスンオンリーへ戻し、MCUを再起動するまで送らない（状態2）。切り替えのとき（CCCRのCCEを立てる）受信のFIFOが空になるので、CAN1の受信が1〜2フレーム欠けることがある（**本体では未確認**）

  - `logger.status`の`obd`：`[状態, 送った数, 拒否した数, 一括の回数]`。状態0＝リッスンオンリーで待ち、1＝問い合わせ中、2＝送信エラーで戻した。`hardware.py`（11/17以降）が画面に出す

  - PCの試験：`tests/test_obd_query.cpp`（WSLのg++。`obdAllowed()`を独立に書いたG-5と1,966,080通りで比べる。偽のECUで一括の読み出し・VINを読まないこと・複数フレームのフロー制御・答えないECU・ハードが断ったとき）と、下の再生の試験台

ビルド時に `image-audit.json`（書き込みサイズとELF静的領域）と `source-manifest.json`（ソースのSHA256）を出力します。静的領域の集計にはコード・定数・BSSを含みますが、LLEXTローダーの追加領域や実行時ヒープの増加を含まないため、ロード成功の保証ではありません。更新時の停止・起動順は共通の `EcoCapture-Web/flash-mcu.sh` で管理します。

ソースを置き換える前にUNO Q側のコピーを確保し、`python compare_sources.py <保存したecologger_v2ディレクトリ>` で改行コードを除いた差分を確認します。比較結果だけで正しい版を自動選択しません。

Bridge RPC: `logger.status` / `logger.take` / `logger.command` / `logger.sdread`。`logger.take`は前回からのIMUの行（`rows`、`[seq,MCU時刻ms,"16進"]`）とCANの受信（`can`）を返して空にします。2026-11-09から、GNSSのNAV-PVTも受け取るたびに`rows`へ同じ形で入ります（16進が92バイトなら解、46バイト・0バイトならIMU。並びは届いた順、時刻は受け取った時刻）。10Hzの解を1つ残らず渡すためで、代わりに`logger.status`の`nav`・`gnss_at`はやめました（RAMの残りが足りないため）。IMUの行・CAN・解は`queueRow`で同じ形に足します。**`logger.status`に`nav`が無いファームは、それを読める`EcoCapture-Web/hardware.py`（2026-11-09以降）を先に入れてから書き込みます**（前の`hardware.py`は`status['nav']`で止まります）。コマンドはメイン処理で実行してcompleted番号で確認します。`LOG1/LOG0`、`C500000`等、停止中の`FILES`、`SD`、`R<sector>`、`H<offset>:<hex>`、`W<sector>`。`R<sector>`は読出し位置を設定して`sector ready`を返します。`logger.sdread`は512バイトを16進形式で返し、次のセクタへ進みます。各読出しで停止状態・パーティション境界を検査します。書き込みAPIは記録中に拒否します。外部へRPCを公開しません。

SDファイルは `EcoCapture-Web/sd_decode.py` でCRC・ブロック連番を確認しCSVへ変換できます。保存時刻はMCU経過時刻で、GNSSの元メッセージも保持します。

SDの記録の種類（1つの記録＝種類1バイト・長さ1バイト・MCUの時刻4バイト・中身）：

| 種類 | 中身 | 長さ |
|---|---|---|
| 1 | IMU（BNO055のレジスタ0x08から） | 46 |
| 2 | NAV-PVTの中身そのまま（10Hz） | 92 |
| 3 | CANの受信（チャンネル・ID・印・長さ・データ） | 7〜15 |
| 4 | IMUが読めなかった印 | 0 |
| 5 | NAV-SATの要約（SP-7-8、1秒に1回）：iTOW（4）・電文の衛星の数・航法に使った衛星・そのうち補強のデータがある衛星・SBASの補強を使った衛星・SLASの補強を使った衛星（各1） | 9 |
| 6 | NAV-SLASの頭（SP-7-8、1秒に1回）：iTOW・版・予約・使った監視局の経度・緯度（1e-3度）・監視局の番号・みちびきの衛星番号・印（bit0 監視局あり、bit1 衛星あり、bit2 試験中）・補正の数 | 20 |
| 7 | 送ったOBDのフレーム（SP-11）：ID（2、リトルエンディアン）・データ8バイト。ハードへ渡せたものだけ | 10 |
| 8 | 一括の読み出しの始まり（SP-11）：理由（1 新しいファイル、2 バスが生きた） | 1 |

`sd_decode.py`は種類5・6を`<CSV>.gnss.jsonl`へ書く（無いファイルでは作らない）。種類7・8と、CAN1の0x7E8のフレームをつなぎ直して読み解いたECUの答え（モード01の値・対応表、03/07のDTC、09のCALID）は`<CSV>.obd.jsonl`へ書く（11/17以降。無いファイルでは作らない）。CSVの列は変わらない。

## PCの再生の試験台（SP-7-9、2026-11-16）

`tests/host/`：ファーム（`logger_impl.h`と、そこから読む`sd_logger.h`・`ubx_parse.h`・`lte_uart.h`）を**手を加えずに**WSLのg++で組み、SUGOの走行の記録を流し込んで論理だけを動かす。ファームのソースには試験台のための`#ifdef`を足していない。

```
python firmware/ecologger_v2/tests/host/test_replay.py
```

しくみ：
- `host_kernel.h`：Arduino・Zephyr・STM32の関数の代わり（`millis`・`delay`・`k_*`のスレッド・ミューテックス・`k_timer`、I2C、`GPIOB`・`FDCAN1`のレジスタ、`String`、`Bridge`）。時計は仮想の時刻で、スレッドは仮想の時刻の順に1本ずつ回す（優先度は本体の設定どおり、ループは5）。コードを走る時間は0で、時刻が進むのは`delay`・`k_msleep`・`k_usleep`・`k_busy_wait`だけ。
- `host_devices.h`：偽の機器。BNO055（読むたびにその時点の最新のサンプルを返し、読んだものを全部控える）、受信機（NAV-PVTを元の時刻にUBXの電文に組み直して出す。NAV-SAT・NAV-SLASは1秒に1回の作り物）、FDCAN1（受信のFIFOは3件。送信は`TXFQS`・`TXBAR`で受け、送ったIDとデータとそのときのモードを控える。標準IDの8バイト以外や、FIFOの書き込み位置の違いは試験の失敗にする。ECUの答えは作らない）、MCP25625（受信のバッファーは2つ）、SDカード（SPIの命令・書き込み後の待ち・128MiBのFAT32）、LEDのシフトレジスター。ビットバンギングのSPIはピンの上げ下げから1バイトずつ読み解く。
- `replay.cpp`：入力を流し、Linuxの側（`server.py`と同じく`logger.status`を0.1秒・`logger.take`を0.05秒ごと）を仮想の時刻の中で動かす。最後に`LOG0`・`FILES0`。`--rpc-port`では代わりにBridgeのRPCを127.0.0.1のTCP（Arduino Routerと同じMessagePack-RPC）で出し、時計を実時間に合わせる。
- `test_replay.py`：3つの段。(1) ふつうの再生、(2) SDの書き込みが途中の10秒、1ブロックごとに0.9秒止まる、(3) `EcoCapture-Web/telemetry_bridge.py`をTCPでつないで実時間で20秒。

**この試験台で確かめられること**
- 電文の読み取り：NAV-PVTが全部、中身そのままSDとLinuxへ行く。NAV-SAT（最大500バイトほど。256バイトずつの読み取りをまたぐ）・NAV-SLASが、1秒に1回の種類5・6になる
- SDの書き方：1MiBのファイルを順に作り（5本目まで）、全ブロックのCRC・連番・ファイル番号、目次の大きさが合い、ふつうのFATの読み手（pyfatfs）で読める。カードの目次はほかのファイル30個であらかじめほぼ埋めてあり、2本目で目次が1区画伸びる（2026-11-11の直し）。受信機はファームが頼んだときだけNAV-SAT・NAV-SLASを出す（古い版は頼まない）。SDのSPIの命令の順番（初期化・読み書き・書き込み後の待ちの間に命令を出さない）、`FILES`の一覧
- 待ち行列の数え方：SDが止まって64KiBの待ち行列があふれると、捨てた数`sd_queue_dropped`とSDから欠けた記録の数が一致し、残った記録は入力の並びのまま。`sd_queue_max`はあふれる手前の65,534B。止まっている間もCAN・Linuxへの行は欠けない（SDの保存のスレッドが待つ間、SPIを離している）
- 取得：CAN1・CAN2の受信が全部、入力と同じ並び・中身で残り、CAN1は元の記録と同じ時刻（ms）になる。IMUは読んだものが全部、読んだ時刻のまま残る。種類ごとに時刻が戻らない（種類をまたぐとCAN1が最大1ms前の時刻で後に来る）
- 状態のJSON：`logger.status`・`logger.take`がJSONとして読め、`hardware.HardwareDecoder`がそのまま読める。`logger.command`（`C500000`・`LOG0`・`FILES0`）、`logger.sdread`でSDのブロックを読める。起動直後は「method logger.status not available」が返り、登録のあとで通る
- ループの監視（`k_timer`）が普通の動きでは働かないこと
- OBDの問い合わせ（SP-11）：送ったフレームが全部G-5に入り、通常モードのときだけで、SDの種類7と同じ並び・中身。種類8は最初が理由2、あとは新しいファイルごとに理由1。最初の送信はCAN1の受信が始まって1秒より後。答えるECUがいないので、一括ごとに0100・03・07・0900の4つ（SUGOの入力で5回、20フレーム）。拒否0

**確かめられないこと**（本体で見る）
- I2C・SPIの速さと、それでループが止まる長さ（コードを走る時間を0にしている）。スレッドの割り込み（優先度による横取り）も無く、切り替わるのは寝るときだけ
- LLEXTのRAMの限界（`build_pc.sh`で本物のコンパイラーで組んで測る）
