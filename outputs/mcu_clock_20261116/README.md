# STM32の時計が遅れて進む件とラップタイム（2026-11-16）

横すべり角の試し（`outputs/slip_angle_20261116/`）で、STM32の時計（`mcu_ms`）が受信機の時計より **−0.26 %** 遅れて進むことが分かった。
ラップタイムに効いていないか、ほかにこの時計で時間を測っている所がないかを調べた。

- スクリプト：`lap_clock_check.py`（SDの NAV-PVT のキャッシュは `slip_angle.py` が作る）

## STM32の時計の進み

| 比べた相手 | 記録 | ずれ |
|---|---|---|
| 受信機の時計（NAV-PVT の itow と、STM32 に届いた時刻） | シールドのSD、11/8〜11/11 の起動15回（0.1〜3.9時間） | −2,590〜−2,660 ppm（短い起動を除く）。決勝の起動は −2,623 ppm |
| 本体の Linux の時計（host_utc） | 11/10 の本体の記録（8.4時間） | −2,615 ppm |

**起動・日をまたいで同じ値**なので、温度などのたまたまではなく、STM32 の発振のくせ（1秒に約2.6 ms 遅い）。水晶の時計なら多くて ±0.01 % 程度なので、それより一桁以上大きい。
（11/8 決勝の本体の記録は、途中で Linux の時計が合わせ直されたらしく、Linux との比べには使えなかった）

## ラップタイムは正しい

- ラップは `EcoCapture-Web/lap.py` が、受信機の UTC（`gnss_utc` の秒＋`gnss_itow_ms` の端数）で、線をまたいだ前後の測位の間を補間して出している。Linux の時計も STM32 の時計も使っていない
- 確かめ：SUGO 11/8 の36周で、記録の LapTime と、SDの測位で線の中心をいちばん近く通った時刻の差から出したラップの差は、**中央値 0.1 ms・標準偏差 4 ms**（倍率 1.00000）
- 同じ周を STM32 の時計で測ると **1周につき 0.295 秒短く**出る（倍率 0.99743）。こちらで測っていたら、ベストラップ 1'50.095 が 1'49.80 になっていた

## STM32の時計を時間として使っている所

| 場所 | 使い方 | 影響 |
|---|---|---|
| **焼き込み録画の針の補間**（`tools/unoq_overlay_enc/tele_smooth.h`、手順書5-24） | サンプルの時刻を `mcu_ms` で持ち、本体の時計との差を「1秒に 0.5 ms まで」ゆるめて追う（`TSM_RELAX`）。PCの試験は「STM32 が1秒に 100 μs ずれる」前提 | **大きい**。実際は1秒に 2.6 ms ずれるので、差の見積もりが1秒に 2.1 ms ずつ遅れていく。PCの試験（`tele_smooth_test.c`）を `DRIFT 1.0026` にすると、カメラの遅れ 60〜150 ms のどれでも**針が止まるコマが 0 % → 32 %**、針が景色より最大 85 ms 先に動き、試験が11件 NG。11/8 に本体で見た「待つ秒が上限 150 ms に張りつく」「上限を 300 ms にすると約2分で上限まで上がる」（1秒に 2.1 ms × 2分 ≒ 250 ms）は、手順書の見立て（たまの大きな遅れ）ではなく、これで説明がつく |
| 走行の一覧の始まりの時刻（`tools/video_collect/run_index.py`） | 終わりの時刻から、`mcu_ms` で測った長さを引いて始まりを出す | 小さい。長さが 0.26 % 短く出るので、2.5 時間の走行で始まりが約 23 秒遅く出る |
| Podium の `Interval`（`EcoCapture-Web/podium.py`）、公式アプリへの `t`（`RaceCapture-UNOQ/rcp_bridge.py`） | `mcu_ms` をそのまま時刻として送る | 小さい。向こうが `Interval` で時間軸を作れば 0.26 % 縮む。ラップタイムは受信機の時刻のまま |
| 解析の道具（`tools/race_analysis/race_analysis.py`・`tools/lap_video/incidents.py`） | `ts = mcu_ms / 1000` で長さ・間隔を測る | ほぼ無い。23 分の停止で 3.6 秒。同じ周どうしの比べは同じ割合で縮むので差はほぼ変わらない。横すべり角の倍率 K に一部吸い込まれていた |
| 解析アプリへの書き出し（`tools/analysis_export/export_session.py`） | 本体の時計を測位の時計で直した時刻を使う | 無い |

STM32 が 10 ms ごとに出すサンプルは、実際には約 10.026 ms ごと（99.74 Hz）。

## 直し方

- 針の補間：**2026-11-16 にPCで直した**（ずれの速さを動きながら測って追う。手順書5-24の追記）。`TSM_RELAX` を上げるだけだと、0.005 で実測のずれは追えるが ±1 % では追えず、上げるほど針が景色より遅れた（0.05 で +23 ms）ので、速さを測るほうにした。本体へ入れるのはユーザーの了承のあと

## まだ直していないもの
- 走行の一覧：長さを `mcu_ms` でなく測位の時刻か本体の時計で測る（または 1.0026 倍する）
- 根っこ：STM32 のファームで時計の元を精度のよいもの（32.768 kHz の水晶で MSI を合わせる・外の水晶）にできるかは、UNO Q の基板に水晶があるかによる（未確認）
